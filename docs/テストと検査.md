# テストと検査

データ・画面・設定を変えたら、次の1つのコマンドで全部を確かめます。

```bash
npm run verify
```

合格すると「すべて合格です。」と表示されます。不合格のときは、最初に表示されたエラーから直してください。

## 何を確かめるか

| 段階 | コマンド | 確かめること |
|---|---|---|
| 1. データの機械検査 | `npm run check` | YAML の形（スキーマ）、ID とファイル名、参照先の存在、名前の重複、規模の参考値の出典・単位、宣伝・推測の表現、個人情報（メールアドレス・電話番号） |
| 2. サイトのビルド | `npm run build` | 検査に通ったデータから、静的サイトを `apps/web/out` に作れること |
| 3. テスト | `npm test` | 下の表のテスト（ビルドの後に実行すると、サイトの検査も行う） |

| テストのファイル | 内容 |
|---|---|
| `tests/lint.test.mjs` | 機械検査が、誤ったデータを正しく見つけること |
| `tests/acceptance.test.mjs` | 既定の版と確認済みだけの版の作り分け、オープンデータ、規模の参考値、秘密情報 |
| `tests/classification-provenance.test.mjs` | 分類の「確認待ち」の印と、その表示 |
| `tests/education.test.mjs` | 12領域・統合階層・評価軸・ライフサイクル・企業業務の流れ・6つの地図がそろっていること |
| `tests/oss-scope.test.mjs` | リポジトリ・サイトのページ・地図が決めた構成どおりであること。秘密情報・外部の AI や計測の呼び出しが入っていないこと |
| `tests/headers.test.mjs` | コメントを書ける全ファイルの先頭に、製作・著作権・ライセンス・ファイルの説明・履歴のヘッダがあること |
| `tests/site.test.mjs` | ビルドしたサイトの内部リンク切れ、外部スクリプト、POST のフォーム、決めた構成の外のページがないこと。カード・製品・地図のページとオープンデータがそろっていること |

## 状況に応じた使い方

| こんなとき | コマンド |
|---|---|
| カードを1枚直しただけで、すぐ確かめたい | `npm run verify:quick`（ビルドを飛ばす。サイトの検査は前回のビルドに対して行う） |
| 公開する前 | `npm run verify` |
| 確認済みだけの版を公開する前 | macOS・Linux：`ATLAS_MODE=reviewed npm run verify`／PowerShell：`$env:ATLAS_MODE = "reviewed"; npm run verify; Remove-Item Env:ATLAS_MODE` |
| サブパス（例：`https://example.github.io/atlas/`）に置く前 | `npm run verify -- --base /atlas` |
| 作ったサイトを画面で確かめる | `npm run start`（http://localhost:3000/） |
| ファイルを足した・コピーした | `npm run headers -- --fix`（ヘッダを付け、パスと説明を直す）、その後 `npm run headers` |

## 自動で実行される検査（GitHub）

| ワークフロー | いつ | 内容 |
|---|---|---|
| `.github/workflows/validate.yml` | Pull Request・main への push | `npm ci` の後に `npm run verify` |
| `.github/workflows/security-scan.yml` | Pull Request・main への push・毎週 | Git の全履歴の秘密情報（TruffleHog）、依存パッケージの既知の脆弱性（OSV-Scanner） |

## 検査を増やすとき

- データの規則は `scripts/lib/lint.mjs` に足し、誤ったデータを見つけられることを `tests/lint.test.mjs` で確かめます。
- サイトの規則は `scripts/lib/site-check.mjs` に足します。
- テストの合格の基準をゆるめて合格させることはしないでください。不合格の原因を直します。
